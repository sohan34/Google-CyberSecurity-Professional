## Logs and Log Management

In this reading, you’ll examine best practices related to log management, storage, and protection. Understanding log collection and management helps improve log searches and support incident investigation.

### Logs

A **log** is a record of events that occur within an organization's systems.

Logs contain log entries, and each entry details information corresponding to a single event that happened on a device or system. Originally, logs served the sole purpose of troubleshooting common technology issues. Today, virtually all computing devices produce some form of logs that provide valuable insights beyond troubleshooting.

Security teams access logs from logging receivers like SIEM tools, which consolidate logs to provide a central repository for log data. Security professionals use logs to perform **log analysis**, which is the process of examining logs to identify events of interest. Logs help uncover the details surrounding the 5 W's of incident investigation:

- who triggered the incident
- what happened
- when the incident took place
- where the incident took place
- why the incident occurred

### Types of logs

Depending on the data source, different log types can be produced. Some common log types are:

- **Network**: generated by network devices like firewalls, routers, or switches
- **System**: generated by operating systems like Chrome OS, Windows, Linux, or macOS
- **Application**: generated by software applications
- **Security**: generated by devices or systems such as antivirus software and intrusion detection systems
- **Authentication**: generated whenever authentication occurs, such as a successful login

### Log details

Generally, logs contain a date, time, location, action, and author of the action.

Example:

Login Event [05:45:15] User1 Authenticated successfully

**Verbose logging** records additional, detailed information beyond the default log recording.

Example:

Login Event [2022/11/16 05:45:15.892673] auth_performer.cc:470 User1 Authenticated successfully from device1 (192.168.1.2)

### Log management

Because all devices produce logs, it can quickly become overwhelming for organizations to keep track of all the logs that are generated. To get the most value from logs, organizations need to choose exactly what to log, how to access it easily, and keep it secure using **log management**.

**Log management** is the process of collecting, storing, analyzing, and disposing of log data.

### What to log

The most important aspect of log management is choosing what to log. Organizations are different, and their logging requirements can differ too. It is important to consider which log sources are most likely to contain useful information depending on the event of interest.

This might include configuring log sources to reduce the amount of data they record, such as excluding excessive verbosity. Some information, including but not limited to phone numbers, email addresses, and names, forms **personally identifiable information (PII)**, which requires special handling and in some jurisdictions might not be possible to be logged.

### The issue with overlogging

It can be tempting to log everything, but this is the most common mistake organizations make. Just because it can be logged does not mean it needs to be logged.

Disadvantages of overlogging include:

- increased storage and maintenance costs
- increased load on systems
- performance issues
- reduced usability
- difficulty searching for and identifying important events

### Log retention

Organizations might operate in industries with regulatory requirements. Some regulations require organizations to retain logs for set periods of time, and organizations can implement log retention practices in their log management policy.

Industries that may need log management changes to meet regulatory requirements include:

- Public sector industries, like the Federal Information Security Modernization Act (FISMA)
- Healthcare industries, like the Health Insurance Portability and Accountability Act of 1996 (HIPAA)
- Financial services industries, such as the Payment Card Industry Data Security Standard (PCI DSS), the Gramm-Leach-Bliley Act (GLBA), and the Sarbanes-Oxley Act of 2002 (SOX)

### Log protection

Along with management and retention, the protection of logs is vital in maintaining log integrity. Malicious actors may modify logs to mislead security teams and hide their activity.

Storing logs in a centralized log server helps maintain log integrity. When logs are generated, they get sent to a dedicated server instead of being stored on a local machine. This makes it more difficult for attackers to access logs because there is a barrier between the attacker and the log location.

### Key takeaways

It is important to understand how to properly collect, store, and protect logs because they are integral to incident investigations. A detailed plan for log management helps improve the usefulness of logs and resource efficiency.

## Log Formats

Security analysts will analyze logs that originate from different sources. Knowing how to interpret different log formats helps determine key information used to support investigations.

### JSON

**JavaScript Object Notation (JSON)** is a file format used to store and transmit data. JSON is lightweight and easy to read and write. It is used for transmitting data in web technologies and is also common in cloud environments.

JSON syntax includes:

- key-value pairs
- commas
- double quotes
- curly brackets
- square brackets

A key-value pair is a set of data that represents two linked items: a key and its corresponding value.

Example:

"Alert": "Malware"

Commas are used to separate data.

Example:

"Alert": "Malware", "Alert code": 1090, "severity": 10

Double quotes are used to enclose text data, also known as strings.

Curly brackets enclose an object, which is a data type that stores data in a comma-separated list of key-value pairs. JSON log entries start and end with a curly bracket.

Example:

"User":
{
    "id": "1234",
    "name": "user",
    "role": "engineer"
}

Square brackets are used to enclose an array, which is a comma-separated ordered list.

Example:

["Administrators", "Users", "Engineering"]

### Syslog

**Syslog** is a standard for logging and transmitting data. It can refer to any of its three different capabilities:

- **Protocol**: used to transport logs to a centralized log server for log management. It uses port 514 for plaintext logs and port 6514 for encrypted logs.
- **Service**: acts as a log forwarding service that consolidates logs from multiple sources into a single location.
- **Log format**: one of the most commonly used log formats. It is the native logging format used in Unix systems.

Syslog log format consists of three components:

- header
- structured-data
- message

Example:

<236>1 2022-03-21T01:11:11.003Z virtual.machine.com evntslog - ID01 [user@32473 iut="1" eventSource="Application" eventID="9999"] This is a log entry!

#### Header

The header contains details like:

- timestamp
- hostname
- application name
- message ID

#### Structured-data

Structured-data is enclosed in square brackets and contains key-value pairs.

#### Message

The message contains a detailed log message about the event.

#### Priority (PRI)

The priority (PRI) field indicates the urgency of the logged event and is contained within angle brackets. Generally, the lower the priority level, the more urgent the event.

**Note:** Syslog headers can be combined with JSON and XML formats. Custom log formats also exist.

### XML

**XML (eXtensible Markup Language)** is a language and format used for storing and transmitting data. XML is a native file format used in Windows systems.

XML syntax uses:

- tags
- elements
- attributes

#### Tags

XML uses tags to store and identify data. Tags are pairs that must contain a start tag and an end tag.

Examples:

- start tag: `<tag>`
- end tag: `</tag>`

#### Elements

XML elements include both the data contained inside of a tag and the tags themselves. All XML entries must contain at least one root element.

Example:

<Event>
    <EventID>4688</EventID>
    <Version>5</Version>
</Event>

In this example, `<Event>` is the root element and contains two child elements: `<EventID>` and `<Version>`.

#### Attributes

XML elements can also contain attributes. Attributes provide additional information about elements and must always be quoted using either single or double quotes.

Example:

<EventData>
    <Data Name='SubjectUserSid'>S-2-3-11-160321</Data>
    <Data Name='SubjectUserName'>JSMITH</Data>
    <Data Name='SubjectDomainName'>ADCOMP</Data>
    <Data Name='SubjectLogonId'>0x1cf1c12</Data>
    <Data Name='NewProcessId'>0x1404</Data>
</EventData>

### CSV

**CSV (Comma Separated Value)** uses commas to separate data values. In CSV logs, the position of the data corresponds to its field name, but the field names themselves might not be included in the log.

Example:

2009-11-24T21:27:09.534255,ALERT,192.168.2.7,1041,x.x.250.50,80,TCP,ALLOWED,1:2001999:9,"ET MALWARE BTGrab.com Spyware Downloading Ads",1

### CEF

**Common Event Format (CEF)** is a log format that uses key-value pairs to structure data and identify fields and their corresponding values.

CEF syntax:

CEF:Version|Device Vendor|Device Product|Device Version|Signature ID|Name|Severity|Extension

Fields are separated by a pipe character `|`. Anything in the Extension part of the CEF log entry must be written in key-value format. Syslog is a common method used to transport logs like CEF.

Example:

Sep 29 08:26:10 host CEF:1|Security|threatmanager|1.0|100|worm successfully stopped|10|src=10.0.0.2 dst=2.1.2.2 spt=1232

Breakdown:

- Syslog Timestamp: `Sep 29 08:26:10`
- Syslog Hostname: `host`
- Version: `CEF:1`
- Device Vendor: `Security`
- Device Product: `threatmanager`
- Device Version: `1.0`
- Signature ID: `100`
- Name: `worm successfully stopped`
- Severity: `10`
- Extension: `src=10.0.0.2 dst=2.1.2.2 spt=1232`

### Key takeaways

There is no single standard format used in logging, and many different log formats exist. Knowing how to interpret different log formats helps determine key information for investigations.

## IDS Technologies and Detection Techniques

This reading examines the different types of intrusion detection system (IDS) technologies and the alerts they produce. It also explores the two common detection techniques used by detection systems.

An intrusion detection system (IDS) is an application that monitors system activity and alerts on possible intrusions. IDS technologies help organizations monitor the activity that happens on their systems and networks to identify indications of malicious activity. Depending on the location you choose to set up an IDS, it can be either host-based or network-based.

### Host-based intrusion detection system

A **host-based intrusion detection system (HIDS)** is an application that monitors the activity of the host on which it is installed. A HIDS is installed as an agent on a host. A host is also known as an endpoint, which is any device connected to a network like a computer or a server.

Typically, HIDS agents are installed on all endpoints and used to monitor and detect security threats. A HIDS monitors internal activity happening on the host to identify any unauthorized or abnormal behavior. If anything unusual is detected, such as the installation of an unauthorized application, the HIDS logs it and sends out an alert.

In addition to monitoring inbound and outbound traffic flows, HIDS can have additional capabilities, such as monitoring file systems, system resource usage, user activity, and more.

### Network-based intrusion detection system

A **network-based intrusion detection system (NIDS)** is an application that collects and monitors network traffic and network data. NIDS software is installed on devices located at specific parts of the network that you want to monitor. The NIDS application inspects network traffic from different devices on the network. If any malicious network traffic is detected, the NIDS logs it and generates an alert.

Using a combination of HIDS and NIDS can provide a multi-layered approach to intrusion detection and response. HIDS and NIDS tools provide different perspectives on the activity occurring on a network and the individual hosts connected to it.

### Detection techniques

Detection systems can use different techniques to detect threats and attacks. The two types of detection techniques commonly used by IDS technologies are signature-based analysis and anomaly-based analysis.

### Signature-based analysis

Signature analysis, or signature-based analysis, is a detection method used to find events of interest. A signature is a pattern associated with malicious activity. Signatures can contain specific patterns like a sequence of binary numbers, bytes, or even specific data like an IP address.

Different types of signatures can be used depending on which type of threat or attack you want to detect. For example, an anti-malware signature contains patterns associated with malware. IDS tools monitor an environment for events that match the patterns defined in this signature. If an event matches the signature, the event gets logged and an alert is generated.

#### Advantages

- Low rate of false positives for known threats

#### Disadvantages

- Signatures can be evaded
- Signatures require updates
- Unknown threats such as new malware families or zero-day attacks cannot be detected

### Anomaly-based analysis

Anomaly-based analysis is a detection method that identifies abnormal behavior. There are two phases to anomaly-based analysis: a training phase and a detection phase.

#### Training phase

A baseline of normal or expected behavior must be established. Baselines are developed by collecting data corresponding to normal system behavior.

#### Detection phase

Current system activity is compared against the baseline. Activity that happens outside of the baseline gets logged and an alert is generated.

#### Advantages

- Ability to detect new and evolving threats

#### Disadvantages

- High rate of false positives
- A pre-existing attacker during training can become part of the baseline and remain undetected

### Key takeaways

- A NIDS monitors an entire network, whereas a HIDS monitors individual endpoints.
- IDS technologies generate alerts when suspicious activity is detected.
- Signature-based and anomaly-based analysis have different strengths and limitations.

## Suricata

**Suricata** is an open-source intrusion detection system, intrusion prevention system, and network analysis tool.

### Suricata features

There are three main ways Suricata can be used:

- **IDS**: As a network-based IDS, Suricata can monitor network traffic and alert on suspicious activities and intrusions. Suricata can also be set up as a host-based IDS to monitor the system and network activities of a single host.
- **IPS**: Suricata can function as an intrusion prevention system to detect and block malicious activity and traffic. Running Suricata in IPS mode requires additional configuration.
- **NSM**: In network security monitoring mode, Suricata helps keep networks safe by producing and saving relevant network logs. Suricata can analyze live network traffic, existing packet capture files, and create and save full or conditional packet captures.

### Rules

Rules or signatures are used to identify specific patterns, behavior, and conditions of network traffic that might indicate malicious activity. The terms rule and signature are often used interchangeably in Suricata.

Suricata signatures consist of three components:

- **Action**: The first component of a signature. It describes the action to take if activity matches the signature. Examples include `alert`, `pass`, `drop`, or `reject`.
- **Header**: Includes source and destination IP addresses, source and destination ports, protocol, and traffic direction.
- **Rule options**: Provide different options to customize signatures.

Rule options have a specific ordering, and changing their order would change the meaning of the rule.

**Note:** Rule order refers to the order in which rules are evaluated by Suricata. Rules are processed in the order they are defined in the configuration file. Suricata’s default order is pass, drop, reject, and alert.

### Custom rules

Although Suricata comes with pre-written rules, it is highly recommended to modify or customize existing rules to meet specific security requirements.

Custom rules help:

- Tailor detection and monitoring
- Minimize false positive alerts

### Configuration file

A **configuration file** is a file used to configure the settings of an application.

Suricata’s configuration file is `suricata.yaml`, which uses YAML syntax.

### Log files

Suricata generates two log files when alerts are triggered:

- **eve.json**: Standard Suricata log file. Contains detailed information and metadata in JSON format. It includes a `flow_id`, which helps correlate related logs or alerts to a single network flow. It is useful for detailed analysis and is better for log parsing and SIEM ingestion.
- **fast.log**: Records minimal alert information, including basic IP and port details. It is a legacy file format and is not suitable for incident response or threat hunting.

### Key takeaways

- Suricata can operate as IDS, IPS, and NSM.
- Custom rules and configuration improve detection capability.
- `eve.json` is more useful than `fast.log` for detailed analysis.

## Log Ingestion and SIEM Searches

### Log ingestion

SIEM tools require data to be effective. **Log ingestion** is the process of collecting and importing data from log sources into a SIEM tool.

The SIEM creates a copy of the event data it receives and retains it within its own storage. This copy allows the SIEM to analyze and process data without directly modifying the original source logs.

### Log forwarders

**Log forwarders** are software that automate the process of collecting and sending log data.

- Some operating systems have native log forwarders
- Others require third-party log forwarding software
- Log forwarders can be configured to send logs to a SIEM

Many SIEM tools use proprietary log forwarders. Others can integrate with open-source forwarders.

### SIEM process overview

The SIEM process consists of three steps:

1. Collect and aggregate data
2. Normalize data
3. Analyze data

This reading focuses on the first step: collection and aggregation.

### Splunk searches

Splunk has its own querying language called **Search Processing Language (SPL)**. SPL is used to search and retrieve events from indexes using Splunk’s Search & Reporting app.

Basic search example:

`index=main fail`

- `index=main` tells Splunk to retrieve events from the `main` index
- `fail` is the search term

Splunk also uses the pipe character `|` to chain commands.

Example:

`index=main fail | chart count by host`

- The first part retrieves matching events
- `|` chains the output to the next command
- `chart count by host` creates a chart of counts by host

A wildcard can expand search results.

Example:

`index=main fail*`

This can return events like `failed` or `failure`.

**Pro tip:** Double quotations are used to search for an exact phrase.

Example:

`"login failure"`

### Google SecOps (Chronicle) searches

In Google SecOps (Chronicle), you can search for events using the Search field and use Procedural Filtering to include or exclude results.

There are two types of searches:

- **Unified Data Model (UDM) Search**
- **Raw Log Search**

#### UDM Search

UDM Search is the default search type. It searches security data that has been ingested, parsed, and normalized. UDM Search is faster than Raw Log Search because it searches indexed and structured data.

All UDM events contain a set of common fields, including:

- **Entities**: provide additional context about a device, user, or process involved in an event
- **Event metadata**: provides a basic description of an event
- **Network metadata**: provides network-related event and protocol details
- **Security results**: provides the security-related outcome of events

Example:

`metadata.event_type = "USER_LOGIN"`

This searches for events relating to user authentication.

#### Raw Log Search

If the needed information cannot be found in normalized data, Raw Log Search can search raw, unparsed logs. It takes longer than UDM search.

Raw Log Search can use items like:

- usernames
- filenames
- hashes
- regular expressions

### Wazuh

Wazuh is a powerful open-source platform that serves as a modern SIEM tool. It is designed to collect, aggregate, and analyze security data to help identify and respond to threats.

The reading includes optional setup instructions for the activity **Perform a query with Wazuh**.

#### Deploy the Wazuh virtual machine

- Download and install Oracle VirtualBox
- Search online for a Wazuh virtual machine OVA file
- Import the appliance into VirtualBox

#### Configure the virtual machine

- Set Base Memory to `4096 MB (4 GB)`

#### Access the Wazuh dashboard

- Start the VM
- Set up a shared folder using the `tutorialdata` folder
- Use the folder name `buttercup-shared`
- Enable Auto-mount
- Fix permissions inside the VM:

`usermod -aG vboxsf root`
`reboot`

- After reboot, run `ip a` to find the VM IP address
- Open the dashboard in a browser using `https://<your_VM_IP_address>`
- Log in with `admin / admin`

#### Ingest and analyze data

- Go to the shared folder:

`cd /media/sf_buttercup-shared`

- Create an ingestion file with `nano ingest.yml`
- Add the provided Filebeat configuration
- Save the file with `Ctrl+X`, `Y`, and `Enter`
- Run ingestion:

`/usr/share/filebeat/bin/filebeat -c ingest.yml -e`

- In the dashboard, open Discover
- Set the time range to Absolute
- Choose an old date such as January 1, 2000
- Search for `*`

### Key takeaways

- SIEM tools need ingested log data to function effectively.
- Log forwarders help automate log collection.
- Splunk, Chronicle, and Wazuh each support searching and analysis in different ways.

## Terms and Definitions from the Course
